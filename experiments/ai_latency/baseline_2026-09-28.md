# AI Latency Baseline — 2026-09-28

Setup: FastAPI backend on localhost, Groq provider, model `openai/gpt-oss-20b`,
`temperature=0`, `max_completion_tokens=60`, `reasoning_effort=low`, shared
`httpx.AsyncClient` (warm connections). Measured server-side with
`time.perf_counter()` around the provider call (`ai_ms`).

| # | Question | Expected | Got | Correct | ai_ms | server_total_ms |
|---|----------|----------|-----|---------|-------|-----------------|
| 1 | Which protocol is connection-oriented? | C (TCP) | C | yes | 679 | 680 |
| 2 | Output range of sigmoid? | B (0 to 1) | B | yes | 411 | 412 |
| 3 | SQL command that removes rows? | B (DELETE) | B | yes | 831 | 832 |
| 4 | Time complexity of binary search? | B (O(log n)) | B | yes | 580 | 580 |
| 5 | Data structure with FIFO order? | B (Queue) | B | yes | 851 | 851 |

## Summary

- Accuracy: 5/5 (100%) — trivially easy set, not a real accuracy benchmark yet
- AI inference latency: min 411 ms, max 851 ms, mean ≈ 670 ms
- Server overhead (validation + orchestration): ~1 ms — negligible
- Confidence: model self-reports 0.99 on all (uncalibrated, expected)

## Observations

- Cold connection (first request after server start) adds ~150–300 ms
  (TLS handshake); warm requests are consistently faster.
- The AI call is 99%+ of server time. Any backend optimization effort
  should target the provider call (smaller model, prompt size, streaming),
  not the FastAPI layer.
